# v0.8.0 application migration and rollback rehearsal

**Date:** 2026-09-30, approximately 03:00–03:12 UTC.

**Result:** migration, snapshot rollback with database restore, and reapplication
passed on a fresh synthetic v0.7.1 installation. All four objects retained their
SHA-256, size, ETag, and content type in every phase.

## Environment and scope

- Isolated Compose project: `lq-ai-080-migration-receipts`, with its own named
  volumes, random test secrets, and shifted localhost ports. No existing user
  deployment or source volume was used.
- Docker Engine 29.8.0, `linux/arm64`, on Apple Silicon.
- Source: `v0.7.1:docker-compose.release.yml`, published v0.7.1 API, gateway,
  web, and proxy images, and cached MinIO pinned by digest.
- Target: release Compose and API image built from
  `99fb25b88a66881093bdc5afa926d4e75d5ce7fe`. The API, both workers, migration CLI,
  and init gate all used that candidate image. The gateway, web, and proxy
  remained on v0.7.1; this was a storage migration test, not qualification of
  the complete four-image v0.8.0 release.
- RustFS: `rustfs/rustfs:1.0.0` pinned to
  `sha256:8cc9801755448b71a786705ce76692c77e14936cccd87cf2fc31842e58f4d1ff`.
- The legacy `MINIO_*` credential and port settings were retained. The target
  used the canonical `object-store` endpoint through the Compose compatibility
  fallbacks.

Exact image identities, Compose hashes, migration output, journal, baseline
manifest, and comparison results are in [receipt.json](2026-09-30-v0.8.0-migration-receipts/receipt.json).
Secrets, authentication tokens, presigned URLs, database dumps, and volume
snapshots are excluded from committed evidence.

## Application-created fixture

Files were uploaded and downloaded through `/api/v1/files` on v0.7.1. The third
was soft-deleted through the API. `/api/v1/users/me/export` queued a real worker
job that completed and wrote the ZIP. The two active files were then attached
to a knowledge base created in the UI. No file or export rows were inserted by
hand.

| Object | Bytes | State before migration |
|---|---:|---|
| `migration-contract.txt` | 13,800 | Active; fictional vendor/payment text |
| `migration-large.txt` | 9,900,000 | Active; two-part upload, ETag ends in `-2` |
| `migration-soft-deleted.txt` | 69 | Soft-deleted in Postgres; retained in S3 |
| Worker-generated export ZIP | 32,683 | Completed and unexpired in Postgres |
| **Total** | **9,946,552** | **Four objects** |

The source database was at Alembic `0066`. A separate custom-format `pg_dump`
was taken after the knowledge-base attachments. The migration snapshot was
10,158,080 bytes, with SHA-256
`98a2f265e0c67d2643d81a4ec29c3c95e871044b56223ad6ab628523e7ea3dd9`.

| Phase | Observation |
|---|---|
| Source baseline | Every upload downloaded with identical bytes; three file rows and one completed export reconciled to four stored objects. |
| `plan --json` | Exit 10, action `apply`, detected `xl-single`; all five preflight checks passed, including database floor, ledger readability, stopped store, and snapshot space. |
| `apply --yes --json` | Exit 0; snapshot and SHA receipt written; ownership migration applied. |
| Target startup | Compose `up -d --wait` passed; candidate API advanced Postgres from `0066` to `0068`. |
| `verify --json` | Exit 0; RustFS readiness 200; exactly four expected keys, no missing or unexpected keys; all three document hashes matched Postgres, including the soft-deleted file. |
| Independent object check | Downloaded all four objects, including the export ZIP; SHA-256, size, ETag, and content type exactly matched the source manifest. |
| Application checks | Both active files returned 200 with matching bytes; the deleted file returned 404; the export stayed completed and its API issued a download URL; both knowledge-base attachments remained. |
| Rollback | Stopped target containers, ran `rollback 0001 --yes --json` successfully, restored the separate database dump, and started cached v0.7.1 images successfully. Full manifest matched the baseline, including database revision `0066`; API checks passed again. |
| Reapplication | Repeated `plan → apply → up → verify`; every object and application check matched again at revision `0068`. |
| Final plan | Exit 0, action `none`, reason `migration is verified`. Volume owner `10001:10001`; both RustFS and retained MinIO format witnesses exist. |

The migration verifier hashes documents against Postgres. It reconciles export
keys but does not have a database hash for their contents. The independent
[manifest reader](2026-09-30-v0.8.0-migration-receipts/read-manifest.py) supplied
that extra check: it reads every stored object's bytes and metadata. The receipt
records identical comparisons after migration, rollback, and reapplication.

## Procedure used

Both Compose definitions used the same isolated project and environment file.
The source override pinned the cached MinIO image; the target override selected
the candidate API for the API, workers, migration CLI, and init gate. The local
`compose.sh source|target` wrapper selected those definitions.

1. Start the source with `up -d --wait`; create the fixture through the API.
2. Save the baseline manifest and `pg_dump -U lq_ai -d lq_ai -Fc`.
3. Stop source containers with `down`, retaining volumes.
4. Run target `run --rm migrate plan --json`, expecting exit 10.
5. Run target `run --rm migrate apply --yes --json`, then `up -d --wait`.
6. Run target `run --rm migrate verify --json`; compare every object and check
   file downloads, deletion, export status, and knowledge-base records.
7. Stop target containers; run target
   `run --rm migrate rollback 0001 --yes --json`.
8. With application containers stopped, recreate **only this disposable test
   database** and restore its pre-upgrade custom dump using `pg_restore
   --exit-on-error`. The object-store rollback does not revert SQL migrations.
9. Start source images and repeat the manifest and API comparisons.
10. Repeat steps 3–6, then run target `migrate plan` and `migrate status` to
    confirm verified state and retention of the snapshot and journal.

## UI evidence and limits

The knowledge-base document list was checked before migration, after migration,
after rollback, and after reapplication. The two names, sizes, attachments, and
5,633 parsed chunks remained visible. File contents were verified through API
downloads; opening a document preview in the UI was not exercised.

Embedding warnings were already present in the source: no embedding-provider
credentials were configured. Parsing completed; this rehearsal makes no claim
about vector retrieval or LLM execution. Export bytes were checked directly
through S3; the issued presigned URL was not fetched from the host browser.

The initial API image build failed because the community-skills submodule was
not initialized. Initializing its pinned commit and rebuilding succeeded. The
first local manifest-reader attempt used the streaming context manager
incorrectly; it was corrected and the baseline was captured before migration.
Neither failure required an application or migration implementation change.

This volume was newly created for the rehearsal. Months of accumulated data,
other MinIO layouts, the oldest supported schema, launcher-driven upgrades,
desktop signing/notarization, and CI's loadable-fixture migration boot were not
tested. The long-lived-installation and launcher evidence in ADR 0036 therefore
remain outstanding. This receipt adds evidence to that ADR without changing its
decision or acceptance criteria.

The isolated stack was left running on RustFS at `http://localhost:23080`, with
the snapshot retained in its operations volume and the database backup retained
privately in `.maintainer/legalquants-lq-ai/releases/v0.8.0/migration-20260930/`.
