# Authoring pages for the documentation site

This directory holds **navigation and generated-page companions only**
(ADR 0028 decision 3; the docs-site mini-PRD). A page's own text lives at its
**canonical repository location** — `docs/`, `skills/`, wherever it already
is — and is mapped onto a route by a **route manifest**. Editing that
Markdown file edits the site; there is no copy to keep in sync. The site
under `site/` builds both halves from the repository at build time.
Nothing in `site/src/content/` is committed — it is generated by
`npm run sync` in `site/`.

This file is not a page. It is the contract a page follows.

## Where a page's Markdown lives

**A page is a plain, GitHub-renderable Markdown file at its canonical
location** — `docs/operate/backup-and-restore.md`, `SECURITY.md`,
`skills/nda-review/SKILL.md`, wherever the repository already keeps it, or a
new file under `docs/<namespace>/` when nothing existing covers the topic.
It carries:

- **no Starlight frontmatter** — none of `title:`/`description:`/`audience:`
  etc. lives in the file;
- an **H1 as its title** — the route manifest defaults the page's title to
  this heading, so a source with no title needs one to be listed without an
  entry `title:`;
- **relative Markdown links**, exactly as any other file in the repository
  writes them, so GitHub renders the page and
  `docs/audits/check_doc_links.py` can verify it.

A route manifest entry (below) is what turns that file into a page: the URL
it gets, its description, audience, status, and its place in the sidebar.

## The route manifest

One YAML file per migration group under `docs/site/routes/*.yaml`; the sync
reads every file in the directory. Each file is a YAML list of entries:

```yaml
- route: operate/backup-and-restore        # URL path, no leading/trailing slash
  source: docs/operate/backup-and-restore.md  # repo-relative Markdown — the page body. Never under docs/site/.
  title: Backup and restore                 # optional; default = the source's first H1
  description: One sentence for search results and llms.txt.   # required
  audience: [operator]                      # operator | evaluator | author | contributor | partner | agent
  status: draft                             # draft | reviewed
  kind: how-to                              # optional; how-to | explanation | reference — sidebar badge + a label near the top
  sources: [docker-compose.yml]             # optional extra files the claims are also checked against
  sidebar:
    order: 3
  next: [operate/upgrade, trust/threat-model]   # optional; renders a trailing "## Next" list of links
  from: "## Troubleshooting"                # optional, discouraged: present only one exact section
  to: "## Something else"                   #   ('to' is exclusive; needs 'from' and/or 'to')
```

`route` and `source` are the only keys every entry needs beyond
`description`. A field the schema does not define, a missing required key, a
`source` that does not exist or sits under `docs/site/`, a route claimed
twice, a source mapped by more than one route, a route that collides with a
page already in `docs/site/`, a `kind` outside `how-to`/`explanation`/
`reference`, and a `next:` target that is not a known route all fail
`npm run sync` with the manifest file, the entry, and what is wrong —
nothing here is silently ignored.

A `kind` is optional, and a page with none renders exactly as it did before
this field existed. Set, it shows up twice: as a Starlight sidebar badge
(`sidebar.badge`, merged in — an entry's own `sidebar: { order: … }` is kept)
and as a short label right under the page title.

The manifest is also what registers the source file in the site's
link-rewrite table: any other page or repository doc linking to
`docs/operate/backup-and-restore.md` lands on `/operate/backup-and-restore/`
automatically, the same as a link to a page still authored under
`docs/site/`.

## What still lives under `docs/site/`

Only navigation and a generated page's own companions:

- `index.mdx` — the entry hub;
- `*/index.md` / `*/index.mdx` — a namespace or nested hub;
- `start/choose-your-path.md`;
- `*.intro.md` — a hand-written lead-in prepended to a generated page of the
  same name (below);
- `_data/` — small YAML files the generators read;
- `routes/` — the route manifests, above;
- this `README.md`.

`npm run check:single-source` is the gate: any other Markdown file under
`docs/site/`, or a manifest `source:` that itself sits under `docs/site/`,
fails it. A page's content belongs at its canonical repository location and
is reached through the route manifest, not through a docs/site wrapper —
that duplication is exactly what ADR 0028 decision 3 rules out.

## Frontmatter on a hub page

A hub (`index.mdx`, `*/index.md`) still carries its own frontmatter, because
it is not mapped from anywhere else:

```yaml
---
title: Is LQ.AI for you?
description: One sentence that a search result or llms.txt can show.   # required
audience: [operator, evaluator]   # operator | evaluator | author | contributor | partner | agent
status: draft                     # draft | reviewed — rendered as a badge
sources:                          # repo-relative files this page curates or checks its claims against
  - docs/quickstart.md
  - README.md
sidebar:
  order: 2                        # position within the namespace
---
```

`title` and `description` are Starlight's. `audience`, `status` and
`sources` are the site's own. `sources` matters: the page's "checked
against" stamp is the newest commit touching the page **or any of its
sources**, so a source that changes makes the stamp move. A route-manifest
entry's `sources:` list does the same job, against its own `source:` file.

## Includes — curation without copies

A hub or other authored page under `docs/site/` that presents an existing
repository file does not copy it. It includes it:

```markdown
<!-- include: docs/quickstart.md -->
<!-- include: docs/INSTALL-MAC.md from="## Install" to="## Troubleshooting" -->
<!-- include: docs/security/threat-model.md shift=1 -->
```

- The path is repository-relative.
- `from` and `to` are exact heading lines in the source; `to` is exclusive.
- The source's H1 is always dropped (the page's `title` replaces it).
- `shift=N` demotes every included heading by N levels.
- Links and images inside the included text are resolved from the source
  file's own location, then rewritten (see below).

A route-manifest entry does not need this directive: its `source:` file
*is* the page body, dropped-H1 and all — that is what "a page's Markdown
lives at its canonical location" means. `from=`/`to=` on an entry slice that
same body the same way `include` would.

## Alerts

A canonical file has to render as a callout on GitHub too, so write the
[GitHub alert syntax](https://github.com/orgs/community/discussions/16925)
rather than a Starlight directive:

```markdown
> [!CAUTION]
> **Silent failure** — a control that fails without telling anyone is worse
> than one that fails loudly.
```

The sync converts `[!NOTE]`, `[!TIP]`, `[!IMPORTANT]`, `[!WARNING]` and
`[!CAUTION]` to a Starlight aside — `note`, `tip`, `note`, `caution` and
`danger` respectively — taking a leading **bold phrase** in the blockquote as
the aside's title. The block above becomes `:::danger[Silent failure]` on the
built page. A page still authored directly under `docs/site/` may write the
Starlight `:::type[]` form instead, since it never has to render on GitHub.

## Next

Every page ends with one to four onward links. A route-manifest entry writes
this as a list of routes, not hand-typed Markdown links:

```yaml
next: [operate/upgrade, trust/threat-model]
```

The sync renders `## Next` with each target's own title, resolved after
every route — authored, generated and mapped — is known; a `next:` entry
naming a route nothing maps fails the sync. A page still authored under
`docs/site/` writes the section by hand instead, as `## Next` followed by
one to four Markdown links.

## Links

Write relative Markdown file links, so that GitHub renders them and
`docs/audits/check_doc_links.py` can verify them — the checker covers a
route-manifest `source:` file exactly as it covers a `docs/site/` page:

| Target | Write | Becomes |
|---|---|---|
| a mapped page (route-manifest `source:`) | `[backup and restore](../../operate/backup-and-restore.md)` | that page's URL |
| another page still authored under `docs/site/` | `[threat model](../trust/threat-model.md)` | the page's URL |
| a repository file some page presents (its `sources[0]`, uncontested) | `[quickstart](../../quickstart.md)` | that page's URL |
| any other repository file | `[SECURITY.md](../../../SECURITY.md)` | a GitHub link pinned to the checked commit |
| an image in the repository | `![](../../images/x.png)` | copied into the site |
| a **generated** page | `[changelog](../changelog/index.intro.md)` | that generated page's URL |

A generated page (`/changelog/`, `/skills/catalogue/`, `/skills/coverage/`,
the three `/reference/` tables) has no ordinary Markdown file anywhere. Link
to its `*.intro.md` companion where it has one — that file exists on disk, so
`docs/audits/check_doc_links.py` can resolve it and GitHub renders it, and
the transform maps it to the generated route. A generated page with no intro
file cannot be linked from a page yet; add the intro file first.

Never write a root-absolute link (`/trust/…`), a hard-coded base
(`/lq-ai/…`), or a `legalquants.github.io` URL. The base path is
configuration. A plain repository URL that happens to contain
`github.com/LegalQuants/lq-ai/…` is not a hard-coded base and is fine.

## What the build adds

- The **stamp**: "Checked against `<sha>` · <date>" and the list of sources,
  in the footer. For a mapped page this is `stampFor(source, sources)` — the
  newest commit touching the `source:` file or any entry in `sources:`.
- The **status badge** from `status`.
- A **`.md` twin** of every page at the page's URL plus `.md`, and the
  site-wide `/llms.txt` and `/llms-full.txt`.
- **Sidebar** placement from the namespace (the first path segment of
  `route:`) and `sidebar.order`. A page not reachable from the sidebar fails
  the build (no orphans).

Do not write any of these by hand.

## Tables

A Markdown table renders as one of three shapes, chosen from its shape rather than
written by hand: two columns become a definition list, one-row-per-entity data (most
tables here) becomes a set of records, and a table stays a plain grid only when it is
both short and narrow enough to fit the column. Write the table normally; if the
automatic choice is wrong for one table, override it with a directive comment
immediately above it — `<!-- table: grid -->`, `<!-- table: dl -->`,
`<!-- table: records -->`, or `<!-- table: records key=2 -->` to title the records from
a column other than the first (1-based). The Markdown source is unaffected either way,
so it still reads as a table on GitHub, whether the page is mapped or still authored
under `docs/site/`.

## House rules

- Every page ends with a `## Next` section of one to four onward links.
- Every claim about what LQ.AI does traces to a file in `sources`. Where the repository
  does not document something, say so — "not documented as of the checked commit" — rather
  than fill the gap.
- A control whose failure is silent says so and says what the reader can observe instead
  (`> [!CAUTION]` with a **Silent failure** lead, or `:::caution[Silent failure]` on a
  page still authored under `docs/site/`).
- Name the professional duty at the point of the decision that engages it
  (`> [!NOTE]` with a **Professional duty** lead), without stating any one jurisdiction's
  rule as universal.
- License obligations are stated as obligations, with the threshold and the compliant pattern.
- Status words come from `docs/HONEST-STATE.md`: shipped, partial, scaffold, deferred.
- Product name: **LQ.AI**. US spelling, as in the rest of the repository.

The quality rules and the journeys these pages are tested against are in the docs-site
mini-PRD (Annexes A and B).
