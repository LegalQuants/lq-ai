**PR #410: preserve the work, but verify the behavior it exposes.**

Its shape is useful: it extends the existing run-now API instead of adding another execution system, keeps the new query optional for existing callers, updates both OpenAPI documents, and reuses the session receipt page. This is a good entry point for #563. It does not provide parallel children, persistent plan approval, or a parent/child receipt tree. Clicking its Run button starts execution immediately; #563 must still add the approval boundary you requested.

1. **[P1] Choosing a knowledge base skips the actual analysis.** The new [KB picker](codex://review?pr=https%3A%2F%2Fgithub.com%2FLegalQuants%2Flq-ai%2Fpull%2F410&path=web%2Fsrc%2Froutes%2Flq-ai%2Fautonomous%2Fmatters%2F%2Bpage.svelte&line=262&side=right) promises to select the documents the run retrieves from. Manual spawning still sets `since=None`, and the new query is simply [copied into params](codex://review?pr=https%3A%2F%2Fgithub.com%2FLegalQuants%2Flq-ai%2Fpull%2F410&path=api%2Fapp%2Fapi%2Fautonomous.py&line=1410&side=right). Existing intake interprets `kb_id` without `since` or `file_id` as a schedule's first tick, sets `first_tick_no_baseline`, and analysis returns before reaching the query planner. This happens even with a populated KB and a valid description. The PR's narrative that retrieval already consumes the KB alongside the query is therefore incomplete. Evidence: [intake at the reviewed head](https://github.com/LegalQuants/lq-ai/blob/961c2c79f01c5a04a7f49d83c710347843ecb565/api/app/autonomous/nodes.py#L151) and [analysis early return](https://github.com/LegalQuants/lq-ai/blob/961c2c79f01c5a04a7f49d83c710347843ecb565/api/app/autonomous/nodes.py#L350).

   **Merge gate:** distinguish manual research from schedule initialization; prove a query with a selected KB reaches the planner and keeps retrieval within that selection. Use stubbed inference/retrieval; useful or nonempty search results are not necessary. Keep a regression for the real schedule-first-tick behavior.

2. **[P2] Entering a cost cap breaks request construction.** The [numeric input](codex://review?pr=https%3A%2F%2Fgithub.com%2FLegalQuants%2Flq-ai%2Fpull%2F410&path=web%2Fsrc%2Froutes%2Flq-ai%2Fautonomous%2Fmatters%2F%2Bpage.svelte&line=282&side=right) binds to a value declared as a string; the [request helper calls `.trim()`](codex://review?pr=https%3A%2F%2Fgithub.com%2FLegalQuants%2Flq-ai%2Fpull%2F410&path=web%2Fsrc%2Froutes%2Flq-ai%2Fautonomous%2Fmatters%2Fintake-helpers.ts&line=77&side=right). Svelte supplies a number after numeric input, or `undefined` after it is cleared. Neither supports `.trim()`, so submission fails before POST. This follows from the code and [Svelte's documented binding behavior](https://svelte.dev/docs/svelte/bind#input-bind:value); the helper tests supply strings and miss the browser boundary.

   **Merge gate:** normalize the input safely and verify typing a decimal, clearing it, and submitting with it untouched. Assert the decimal-as-string API payload and an actual POST from the form.

3. **[P1] Clear the planner's data-handling gap before exposing confidential intake.** This is existing executor behavior newly made reachable by #410's query field: the [planner passes the raw goal with `anonymize=False`](https://github.com/LegalQuants/lq-ai/blob/961c2c79f01c5a04a7f49d83c710347843ecb565/api/app/autonomous/nodes.py#L212), and the [gateway request construction](https://github.com/LegalQuants/lq-ai/blob/961c2c79f01c5a04a7f49d83c710347843ecb565/api/app/autonomous/guard.py#L1530) does not forward the selected project's tier floor or privileged flag. Deployment-wide routing policy still applies, but it cannot enforce project metadata it never receives. On an otherwise permitted external route, the new description can therefore bypass the normal anonymization request and project-specific restriction.

   **Merge gate:** resolve and forward the authoritative project/skill restrictions through the autonomous path and verify the planner, tool calls and synthesis honor them. Resolve anonymization deliberately for free-text goals and observations. A companion corrective PR is reasonable; this need not become the entire #563 implementation.

The recorded [API/Web/Gateway checks](https://github.com/LegalQuants/lq-ai/actions/runs/30156190960) are positive evidence for the tested surface. The added Cypress test intercepts the execution endpoints, does not exercise the selected-KB executor path, and was not run according to the PR body. Green CI does not cover the three gates above.

**PR #536: the access model is promising, but the claimed guarantees exceed the implementation.**

Centralizing matter access, defaulting existing matters to personal, and making a block override ordinary grants are sensible foundations. However, the change extends ownership into revocable membership, which requires checks after initial creation as well as at creation time.

1. **[P1] Blocking a member does not revoke their own matter chats.** A contributor can create a chat while authorized, then be changed to `blocked`. The new [read loader returns immediately for the chat owner](codex://review?pr=https%3A%2F%2Fgithub.com%2FLegalQuants%2Flq-ai%2Fpull%2F536&path=api%2Fapp%2Fapi%2Fchats.py&line=405&side=right), before resolving matter access. Message posting still uses the owner-only loader, so the same person can continue the chat as well. The new screened-member test only checks access to someone else's chat. The absolute-denial guarantee is not satisfied.

   **Merge gate:** check current matter authorization on reads and writes of associated chats, with tests for a former contributor's own chat after blocking, removal and demotion. Preserve author-only writing in addition to the matter permission check. Audit queued sessions, schedules and watches for the same revoked-authority problem before calling the screen complete.

2. **[P1] Sandbox privacy can be bypassed through membership.** The new [member-creation endpoint](codex://review?pr=https%3A%2F%2Fgithub.com%2FLegalQuants%2Flq-ai%2Fpull%2F536&path=api%2Fapp%2Fapi%2Fmatter_members.py&line=179&side=right) lets a sandbox owner add another person. The resolver grants that membership without checking `is_sandbox`. The database constraint only requires `share_scope='personal'`, which remains true throughout this sequence. Thus the PR's “can never be shared” claim is false even though its test rejecting `share_scope='org'` passes.

   **Merge gate:** reject non-owner grants to sandboxes and enforce sandbox privacy consistently in both individual access and list filtering. Test the membership API, not only share-scope changes.

3. **[P1] The deletion safeguard runs after irreversible byte deletion.** The [new shared-project check](codex://review?pr=https%3A%2F%2Fgithub.com%2FLegalQuants%2Flq-ai%2Fpull%2F536&path=api%2Fapp%2Fworkers%2Fuser_deletion.py&line=124&side=right) intentionally leaves owned shared matters in place so their restrictive foreign key prevents user deletion. But `_hard_delete_user` already deleted stored export and file bytes earlier in the function. The database transaction then fails and rolls back, while deleted bytes cannot roll back with it. This can leave retained rows and shared attachments pointing to missing objects. The new `added_by_user_id` restrictive reference also needs an explicit deletion policy.

   **Merge gate:** preflight ownership/membership retention blockers before deleting any bytes; resolve ownership transfer or an explicit retained-identity policy; test that a blocked deletion makes zero storage-delete calls. The current comment that a failed transaction leaves the user's state intact is not true for object storage.

4. **[P2] The actual CI failure is an unrelated route expectation.** The [new OpenAPI expectation](codex://review?pr=https%3A%2F%2Fgithub.com%2FLegalQuants%2Flq-ai%2Fpull%2F536&path=api%2Ftests%2Ftest_openapi.py&line=118&side=right) includes `/api/v1/admin/users/{user_id}/reset-password`, which this PR does not implement. The [failed API job](https://github.com/LegalQuants/lq-ai/actions/runs/32490188310/job/96795757036) reports **1 failed, 2,692 passed, 1 skipped** and names this missing path. This is different from the two pre-existing failures described in the PR narrative. Remove the unrelated expectation/documentation, or make the provisioning dependency explicit; do not merge another PR merely to hide the mismatch.

There are also product decisions to settle in its ADR: what `personal` versus `members` means when both accept explicit grants; how an operator recovers a matter without an existing lead; and the exceptions retained for auditor/receipt access. The new ADR labels itself Accepted while recording that it was written after implementation; maintainers should explicitly ratify the final behavior. The canonical OpenAPI sketch should be reconciled with the new endpoints. No frontend membership-management UI is included, and file/KB sharing is explicitly deferred, so merging #536 would not complete collaborative matter research.
